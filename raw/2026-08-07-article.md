## Summary
文章說明瀏覽器主執行緒同時承擔 JavaScript、使用者輸入與畫面渲染；真正造成卡頓的往往不是程式碼本身很慢，而是它長時間占住主執行緒。改善方向包含切分、批次處理、優先排序、延後非必要工作，以及把重度運算移到主執行緒之外。

DOM이나 스타일이 바뀌어 화면을 갱신할 일이 생기면 브라우저는 대략 다음 단계를 순서대로 거쳐 한 프레임을 만든다. requestAnimationFrame 콜백 실행 - 프레임을 그리기 직전에 실행하기로 등록해둔 자바스크립트 스타일 계산 - 각 요소에 적용될 최종 CSS 값을 계산 레이아웃 - 각 요소의 위치와 크기를 계산 (리플로우 reflow 라고도 부름) 페인트 - 무엇을 어떤 색으로 그릴지 페인트 명령을 만든다 바뀐 것이 없으면 이 단계들은 통째로 건너뛰므로 매 프레임 반드시 도는 것은 아니다. 그리고 이렇게 만들어진 결과를 넘겨받아 화면에 합치는 합성 단계만이 컴포지터 스레드 1 로 넘어간다. 즉, 화면을 그리는 파이프라인의 앞쪽 대부분이 메인 스레드의 몫이다. 화면을 갱신할 때 거치는 렌더링 파이프라인 화면이 부드럽게 보이려면 디스플레이의 주사율만큼 프레임을 그려야 한다. 가장 흔한 60Hz 디스플레이 기준으로 초당 60프레임, 즉 한 프레임에 주어진 시간이 약 16.6밀리초 다. 이마저도 통째로 쓸 수 있는 것이 아니다. 브라우저 자체의 처리 비용을 빼면 실제 가용 예산은 10밀리초 남짓으로 보는 것이 보통이고 2 , 주사율이 120Hz인 기기라면 예산 자체가 절반으로 줄어든다. 문제는 앞서 본 두 종류의 일이 같은 스레드에서 한 줄로 선다 는 것이다. 자바스크립트는 단일 스레드 이벤트 루프 모델로 설계되었다. 메인 스레드는 한 번에 하나의 작업만 처리하며 그 작업이 실행되는 동안에는 다른 어떤 것도 할 수 없다. 만약 자바스크립트 함수 하나가 200밀리초 동안 돌고 있다면 200밀리초 동안 브라우저는 화면을 다시 그리거나 사용자의 클릭을 받지 못한다. 10밀리초 남짓의 프레임 예산 앞에서는 아주 치명적인 시간이다. 이렇게 오래 실행되어 메인 스레드를 붙잡는 작업을 롱 태스크라 부르며 보통 50밀리초를 넘기면 문제로 간주한다. 말로만 들으면 와닿지 않으니 직접 느껴보자. 아래 데모에서 버튼을 누르면 자바스크립트가 잠시 메인 스레드를 붙잡는다. JS 애니메이션 메인 스레드 · rAF CSS 애니메이션 컴포지터 · transform 0.5초 막기 2초 막기 버튼을 누르면 JS 애니메이션과 입력은 멈추지만 CSS 애니메이션은 계속 돈다 버튼을 누른 순간 JS 애니메이션은 멈추고 입력창에 글자를 쳐도 반응이 없다. 반면 CSS 애니메이션은 계속 돈다. 이 차이가 어디서 오는지는 뒤에서 다시 이야기하겠다. 지금 기억해야 할 것은 메인 스레드를 오래 붙잡는 것은 곧 화면을 멈추는 것과 같다 는 사실이다. 이러한 점은 웹 성능 지표와도 곧바로 연결된다. 사용자가 무언가를 눌렀을 때 화면이 반응하기까지의 시간을 재는 INP Interaction to Next Paint 나 페이지 로딩 중 메인 스레드가 막혀 있던 총 시간을 재는 TBT Total Blocking Time 같은 지표들은 결국 “메인 스레드가 얼마나 오래 막혀 있었는가”를 표현한 것에 가깝다. 성능 최적화란 상당 부분 이 하나의 스레드를 어떻게 아껴 쓰느냐의 문제인 셈이다. 그리고 그 방법은 크게 둘로 나뉜다. 하나는 메인 스레드 안에서 시간을 잘 나눠 쓰는 것이고 다른 하나는 아예 일을 메인 스레드 바깥으로 내보내는 것이다. 차례대로 살펴보자. 비싼 자원을 아껴 쓰기 첫 번째는 메인 스레드를 쓰면서 시간을 영리하게 쓰는 것 이다. 핵심은 네 가지다. 너무 긴 작업을 어떻게 잘게 나눌 것인가 너무 잦은 작업을 어떻게 묶을 것인가 여러 작업 중 무엇을 먼저 할 것인가 지금 꼭 안 해도 되는 작업을 어떻게 미룰 것인가 여기서는 각각 쪼개기, 모으기, 우선순위, 미루기라고 부를 것이다. 앞의 둘은 태스크의 크기 를 다듬는 일이고 뒤의 둘은 실행의 시기 를 정하는 일이다. 그리고 이 중 쪼개기가 나머지의 기반이 된다. 태스크에 경계가 생겨야 비로소 그 사이에 무엇을 먼저 넣고 무엇을 뒤로 보낼지도 정할 수 있기 때문이다. 그래서 쪼개기부터 시작한다. 쪼개기 라이브 스트리밍 방송의 채팅창을 떠올려보자. 인기 방송에서는 채팅이 순간적으로 초당 수백 개씩 쏟아질 때도 있다. 이런 환경에서 채팅은 하나씩 얌전히 도착하지 않는다. 트래픽이 몰리면 서버가 수십 개씩 뭉텅이로 보내기도 하고 방에 입장하는 순간에는 밀린 채팅 수백 개가 한꺼번에 내려오기도 한다. 이 덩어리를 받은 즉시 한 호흡에 전부 그린다면 어떻게 될까? 채팅 하나를 그릴 때마다 DOM 생성과 스타일 계산, 레이아웃, 페인트가 따라붙는데 그 수백 번이 하나의 태스크 안에서 연속으로 실행된다. 그동안 사용자가 자기 채팅을 입력하려 해도 입력창은 버벅이고 화면의 다른 애니메이션도 끊긴다. 쏟아지는 남의 채팅이 메인 스레드를 독차지해 내 입력을 방해하는 셈이다. 해법은 앞서 이야기한 그대로다. 이 덩어리를 작은 조각으로 나누고 조각과 조각 사이에서 메인 스레드에 잠깐씩 제어권을 돌려주면 된다. 그 틈에 브라우저는 밀려 있던 화면 갱신과 입력 처리를 해낼 수 있다. 아래 예제는 스트리밍 방송의 채팅창을 시뮬레이션한 것이다. “채팅 쏟아지게 하기”를 누르면 채팅이 쉴 새 없이 올라온다. 이때 입력창에 직접 타이핑해보고 위쪽의 부드러움 지표와 fps를 지켜보면서 “즉시 렌더”와 “양보 렌더” 모드를 각각 확인해보자. 부드러움 지표 (JS 애니메이션) 60 fps 즉시 렌더 양보 렌더 채팅 쏟아지게 하기 “즉시 렌더”
