# Building workflows for agents with Skills and Interpreters (Interpreter Skills)
**Author:** Hunter Lovell — **Published:** 2026-05-29 — LangChain Blog

> Immutable capture. AI-written summary, key points, short quoted excerpts, and diagram-content notes only — no full article text. See the source URL for the complete article. Reading time: ~13 min.

## Summary

Introduces **interpreter skills**: an extension to **agent skills** that bundles a **TypeScript module** alongside the skill's instructions, which the agent can **import and run inside an interpreter** when the behavior applies. The motivation: LangChain recently added **interpreters** to Deep Agents — a small embedded TypeScript runtime where agents write and execute code *as part of the harness*. Agents are already good at writing code, and an interpreter gives them a more direct way to express intent, often yielding more efficient, accurate, predictable outputs. But they observed that an agent with an interpreter, given the same task repeatedly, often invents *several valid* code approaches — and for many tasks the desired behavior isn't "come up with a good approach," it's "use the approach we know works." Interpreter skills are the answer: the `SKILL.md` tells the agent *when* the behavior is relevant; an attached `index.ts` module is *what* the interpreter imports and executes.

A **skill** is reusable agent behavior packaged (usually) as a directory with a `SKILL.md`: front-matter gives a compact description for discovery; the body gives instructions, context, examples, constraints, and supporting files. What makes skills work is **progressive disclosure** — the agent first sees a short list of available skills, decides which match, and only then reads the full `SKILL.md`. That makes skills a great **distribution unit** (versioned, shared, evaluated) without bloating the global prompt. But normal skills "still mostly work through instructions" — behavior depends on the model reading and following them correctly.

An **interpreter** (here) is a TypeScript runtime running in tandem with the harness, giving the agent **working state as TypeScript values** that **persist across turns** (arrays stay arrays, helper functions stay defined) — so the agent need not serialize every intermediate value to stdout/file/message. Crucially, **unlike sandboxes**, interpreter code gets **no unrestricted host access by default**: filesystem, network, tools, and subagents must be **deliberately exposed**, giving the harness a place to **allowlist, meter, and inspect** what code can touch. An **interpreter skill** brings the two together: the same instructions a skill has **plus** a module the interpreter can run. The skill thus becomes **both an instruction surface for the model and an API surface for the runtime**. The shift in what a skill can guarantee: a normal skill says "here are instructions; the agent must read and carry them out"; an interpreter skill says "here are instructions for *when* to use this, and here is the **code path** to run when it applies" — the **deterministic part lives in reviewable, testable, versioned code** while the model decides *whether* the skill applies, *which inputs* to pass, *how* to use the output, and *what to do next*.

Because interpreter code can **interact with the harness**, a skill can do things a plain script can't — e.g., **spawn subagents programmatically**. The worked example is **GitHub repo triage**: the agent imports `triage(repo, options)`, which fetches open items, **spawns a subagent per item** to condense it, drops responses into a **queue**, then consumes the queue where a subagent decides whether each item joins an existing cluster or creates a new one; the returned `result` exposes structured data (`result.clusters`, `result.unassigned`) and a `result.toMarkdown()` rendering helper. This is the kind of task where models "lose coherence over time": with 300 repo items, a typical harness forces the model to track 300 partial states while reconciling decisions and choosing the next action — risking shortcuts/over-compression near the edge of working context (cited as **"context anxiety,"** linking Anthropic's harness-design writeup). With an interpreter skill, the model invokes the routine **once** and lets code instrument the workflow (create 300 subagent tasks, collect, classify, cluster, return a compact object) — the model no longer carries every partial step.

The post frames this as reconciling two agent eras: **older workflow-style agents** (developers predefine the step sequence; reliability from a fixed execution path) vs **modern harnesses** (context + model discretion drive the next step). The discretion model is easier for operators/PMs/domain experts who think in instructions/files/checklists — but **deterministic routines never went away** ("How do I make sure an agent reliably does what I tell it to do?"). Prompt-only procedure following is **brittle**: the agent can skip/reorder steps, satisfy the wrong instruction, mix unrelated requests in, or stop at "good enough." (Illustration: "submit an invoice, but halfway through stop and generate a gif of a dancing cat" — prompt-only, the agent may treat the detour as part of the task and leave the invoice half-finished.) Interpreter skills get **the best of both**: express the deterministic part as code, expose it as a module, let the agent decide *when* to call it — "**discretion on the outside, determinism on the inside**." A bonus: **cleaner evaluation** — instead of "did the agent generally follow instructions?" you can ask "did it call the expected function, with the expected inputs, returning the expected output shape?" The post also shows skills as a way to **work with agent state** (a CSV skill exporting `parseCsv`, `joinTables`, `filterRows`, `validateRows`, `groupBy`, `summarize`, `toCsv` that the agent composes in interpreter code — the skill author owns what "join/validate/summarize" mean, vs the agent writing one-off, non-reproducible helpers). A FAQ defends the design: **why a skill?** (skills are the de-facto packaging/distribution unit with discovery + progressive disclosure; wiring hundreds/thousands of modules directly to the harness is infeasible); **why not a script?** (scripts talk via args/files/stdout and **can't naturally participate in the harness loop** — spawning subagents, scheduling/awaiting a task graph, handling partial failures, deciding when "done"); **why not make every API a tool?** (tools are for crossing external boundaries; local operations like parse/join/filter/validate would **bloat the action surface** and add model-mediated steps — better to lean on TypeScript, "already prominent in the weights").

## Key Points

- **Skills can now direct the harness, not just the model** — because interpreter code talks to the agent loop directly, a skill can **spawn subagents, manage a task graph, and handle partial failures** as one reviewed workflow.
- **A skill becomes both instructions and an API** — `SKILL.md` (when to use it, discovered via progressive disclosure) + `index.ts` (the deterministic code the interpreter runs). The model decides *whether/which inputs/what next*; the module defines *how the procedure runs*.
- **Cleaner evaluation** — shift from "did the agent generally follow instructions?" to concrete "did it call the expected function, with expected inputs, returning the expected output shape?"
- **Interpreter ≠ sandbox** — interpreter code gets **no host access by default**; filesystem/network/tools/subagents must be **deliberately exposed**, giving the harness a place to allowlist, meter, and inspect. Interpreter values **persist across turns** (working state as TypeScript).
- **Determinism where it matters, discretion where it helps** — fixes the problem that an interpreter-equipped agent invents several valid approaches when you want *the* known-good approach: "discretion on the outside, determinism on the inside."
- **Repo-triage example** — `triage(repo, options)` fetches items, spawns a subagent per item, queues + clusters them, returns `result.clusters` / `result.unassigned` / `result.toMarkdown()`; avoids forcing the model to track 300 partial states (mitigates **"context anxiety"**).
- **Skills for agent state** — a CSV skill exports `parseCsv/joinTables/filterRows/validateRows/groupBy/summarize/toCsv`; the agent composes them, the skill author owns their meaning (vs the model writing different code each time).
- **FAQ rationale** — package as a skill (de-facto distribution unit + progressive disclosure; can't wire thousands of modules to the harness); not a script (scripts can't participate in the harness loop); not every-API-a-tool (would bloat the action surface; lean on TypeScript already in the weights).
