# Evaluating Deep Agents: Our Learnings

## Summary

A LangChain engineering post distilling five patterns the team learned while writing evals for **four applications shipped on the Deep Agents harness over one month**: **DeepAgents CLI** (a coding agent), **LangSmith Assist** (an in-app LangSmith helper agent), a **Personal Email Assistant** (an email agent that learns per-user from interactions), and **Agent Builder** (a no-code agent-building platform "powered by meta deep agents"). The thesis is that **deep agents break the assumptions of traditional LLM evaluation**, where every datapoint runs through the same application logic and is scored by the same evaluator. Deep agents are long-running, stateful, multi-step, and produce more than a final message, so evals must test the **trajectory**, the **final response**, and **other state** (files, artifacts), often with **per-datapoint, bespoke success criteria written in code**.

The post defines three **ways to run an agent** for evaluation — **single step** (constrain the core loop to one turn to inspect the next action), **full turn** (run the agent end-to-end on one input across multiple tool-calling iterations), and **multiple turns** (run it repeatedly to simulate a multi-turn user conversation) — and three **things to test**: **trajectory** (sequence of tools called and their arguments), **final response**, and **other state** (e.g. files, artifacts).

The five learnings: (1) **Deep agents require more bespoke per-datapoint test logic (code)** — each test case has its own success criteria, asserting against trajectory, final message, and state; LangSmith's Pytest/Vitest integrations support this and auto-log each test case to an experiment with traces for debugging. (2) **Single-step evals are valuable and efficient** — about half of LangChain's deep-agent test cases were single-step ("what did the LLM decide immediately after a series of input messages?"), useful for validating the right tool was called with the right args; regressions often occur at individual decision points; LangGraph's `interrupt_before=["tools"]` lets you stop before the tools node and inspect tool-call args without running the full sequence (and it saves tokens). (3) **Full agent turns give a complete picture** — single-step evals are like "unit tests"; full turns test trajectory (a tool was called *at some point*, order-independent), final response (matters more for open-ended tasks like coding and research), and other state (read/test files a coding agent wrote; assert a research agent found the right links/sources). (4) **Multiple turns simulate full user interactions** but must be "kept on rails" — naively hardcoding a sequence of user inputs breaks if the agent deviates, so they add conditional logic (run turn 1, check output; if expected, run next turn; else fail early), and can start a test from a later turn with appropriate initial state. (5) **Environment setup matters** — deep agents need fresh, clean, reproducible environments per eval run or evals become flaky; e.g. **Harbor** provides a Dockerized/sandboxed eval environment for TerminalBench, while DeepAgents CLI uses a lightweight temp directory per test; **mock/replay API requests** (`vcr` for Python; proxy `fetch` through a Hono app for JS) to make evals faster, cheaper, and debuggable when the agent depends on external state (e.g. LangSmith Assist hitting real LangSmith APIs).

The post closes by noting you likely need only a **subset** of these patterns for any given application, so an evaluation framework should be flexible, and points readers to LangSmith's testing integrations (Pytest/Vitest beta).

## Key Points

- **Context:** four deep-agent apps shipped on the Deep Agents harness in ~1 month — DeepAgents CLI (coding), LangSmith Assist (in-app), Personal Email Assistant (learns per user), Agent Builder (no-code, "meta deep agents"). Each needed its own evals.
- **Traditional LLM eval** = build dataset → write one evaluator → run app over dataset and score every output identically. **Deep agents break this**: you test more than the final message, and success criteria are often per-datapoint.
- **Glossary — ways to run an agent:** **Single step** (constrain core loop to one turn → next action); **Full turn** (run end-to-end on one input, possibly many tool-call iterations); **Multiple turns** (run in full repeatedly → simulate multi-turn conversation).
- **Glossary — things to test:** **Trajectory** (sequence of tools called + tool arguments); **Final response** (returned to user); **Other state** (files, artifacts the agent generated).
- **Learning #1 — bespoke per-datapoint test logic.** Each test case has its own success criteria and assertions against trajectory/final message/state. Worked example: a **calendar-scheduling deep agent that remembers preferences** — user says "remember to never schedule meetings before 9am"; assert (a) agent called `edit_file` on `memories.md`, (b) it communicated the update in its final message, (c) `memories.md` actually contains the info (regex for "9am" **or** LLM-as-judge for a holistic check). LangSmith Pytest/Vitest support this; auto-logs test cases to an experiment with traces.
- **Learning #2 — single-step evals are valuable + efficient.** ~half of their test cases. Validate the correct tool was called with correct args (right meeting-time search, right directory inspection, memory update). Regressions often happen at individual decision points, not across full sequences. LangGraph streaming lets you `interrupt_before=["tools"]` to inspect output after one tool call (catches issues early, saves tokens).
- **Learning #3 — full agent turns give a complete picture** ("integration tests" to single-step's "unit tests"). Test three ways: **Trajectory** (a tool was called at some point, timing-agnostic — scheduler may need many calls to find a slot); **Final Response** (quality of output matters more for open-ended coding/research); **Other State** (coding agent → read and test files it wrote; research agent → assert it found the right links/sources). LangSmith shows full turns as traces with latency/token metrics down to each model/tool call.
- **Learning #4 — multiple turns simulate full user interactions.** Challenge: hardcoded input sequences break when the agent deviates. Fix: conditional logic in Pytest/Vitest — run a turn, check output; if expected → next turn; if not → fail early. Can also test turn 2 or 3 in isolation by seeding initial state. Avoids modeling every agent branch.
- **Learning #5 — eval environment setup matters.** Deep agents are stateful + long-running, needing a fresh/clean/reproducible environment per run (vs simpler, stateless-tool LLM evals). Coding example: **Harbor** runs TerminalBench inside a dedicated Docker container/sandbox; **DeepAgents CLI** uses a lightweight temp directory per test. Reset-per-test or evals become flaky/irreproducible.
- **Tip — mock/replay API requests.** Live services are slow/expensive (LangSmith Assist hits real LangSmith APIs). Record HTTP into a filesystem and replay during tests: **`vcr`** for Python; proxy `fetch` through a **Hono app** for JS. Faster, cheaper, easier to debug when the agent leans on external system state.
- **Closing:** you likely need only a **subset** of these patterns; keep the eval framework flexible. Pointer to LangSmith Pytest/Vitest testing integrations (beta).
- **Short quoted excerpts:** "Deep agents require bespoke test logic for each datapoint — each test case has its own success criteria." · "Regressions often occur at individual decision points rather than across full execution sequences." · "Deep Agent evals require environments that resets per test -- otherwise your evals become flaky and difficult to reproduce." (typos in source).
