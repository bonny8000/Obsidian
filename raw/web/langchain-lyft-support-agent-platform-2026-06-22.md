# How Lyft Built a Self-Serve AI Agent Platform for Customer Support with LangGraph and LangSmith

**Author / Company:** Akshay Sharma (Machine Learning Engineer, Lyft) — guest post from Lyft's SCX Data Science & MLE team **Published:** 2026-05-27 — LangChain Blog (Case Studies / LangGraph / LangSmith / Tutorials & How-Tos)

## Summary

A Lyft guest post (on the LangChain blog) describing how Lyft's **SCX Data Science and MLE team** built a **self-serve AI agent platform** for customer support, so that **non-technical domain experts** (ops teams, Voice-of-Customer leads, product managers) can build and operate AI agents directly via prompts and configuration — without an MLE in the daily loop. Lyft's **AI Assist** handles customer support for riders and drivers across categories like account access, damage claims, charge reviews, and earnings disputes, managing millions of interactions.

The motivation: Lyft's agent work began in **2023**, but each agent demanded months of MLE/engineering effort. The development cycle was a slow loop — domain experts defined workflow behaviors, MLEs translated them into tool configs and prompts, then both reviewed traces, flagged problems, and adjusted code over weeks. By 2026 demand surged (new user segments, more issue types, autonomous-vehicle support), making the model unsustainable. The pivotal question: could ops teams, VoC leads, and PMs **construct and refine agents directly using natural language**, removing the technical middleman — **without compromising experience, accuracy, or safety**? Every agent still had to match the quality of manually engineered systems.

**Architecture** is a **router multi-agent system on LangGraph** (LangGraph's "router multi-agent architecture"). A **meta agent** acts as a stateful router: it classifies the incoming request and uses `Command(goto=...)` to dispatch to the appropriate specialized **subagent**. Each subagent is a full LangGraph `StateGraph`, registered as a subgraph node in the meta agent. Lyft runs **separate router instances for riders and drivers**: a rider contact routes to a `rider_intent` subagent (lost items, charge disputes, trip issues); drivers route to a `driver_intent` subagent (earnings, account access, damage claims). If an intent agent decides mid-conversation that a more specialized agent is needed, it uses `Command(goto=..., graph=Command.PARENT)` to hand control back to the meta agent, which re-routes (e.g. jumping from the driver intent agent to the damage claim agent mid-conversation).

Each subagent follows a **consistent node pattern**, giving two properties: (1) **safety runs in parallel at every turn** — malicious-intent detection and safety-issue detection execute concurrently via LangGraph's `Command(goto=[...])` fan-out **before any LLM reasoning happens**; and (2) **subagents are modular and independently deployable** — adding an agent means defining a new subgraph and registering it with the meta agent.

There are **two agent categories**: **Specialized agents**, hand-built by MLEs for complex, high-stakes workflows (e.g. the **damage claim agent** with image processing, fraud detection, multi-step classification, and automation calls too complex for low-code); and **Configurable agents**, the self-serve layer, **initialized at runtime from JSON configuration** stored in an internal config service, with **prompts pulled from LangSmith's Prompt Hub**. A domain expert writes a prompt following a structured template (role, scope, workflow phases, content guidelines), and a `ConfigurableAgent` class handles graph construction, tool binding, safety gates, and state management. So a PM can define a new agent (e.g. driver tax questions) by writing a prompt + JSON config — **no MLE code changes**. **State persistence** uses a custom `DynamoDBSaver` implementing LangGraph's `BaseCheckpointSaver`, storing full graph state, execution metadata, and parent-checkpoint references for replay/debugging/inspection.

**LangSmith** provides production tracing (every agent invocation across dev/staging/prod, `LANGSMITH_TRACING=true`), capturing which nodes ran, what the LLM saw, tools called, token usage, and latency per step. Traces are enriched with custom metadata (user type, agent name, intent, conversation ID) for filtering — letting the team pull an exact trace and localize an issue to intent classification, tool execution, or final LLM response "within hours." Before any agent reaches 100% traffic it must pass an **LLM-as-a-Judge evaluation pipeline**: small production rollout (5–10%) → sample production traces as eval datasets → run LLM-as-a-Judge evaluators (a shared judge-prompt template from Prompt Hub, extended with agent-specific metrics). Domain-specific metrics are added per specialized agent (e.g. the core earnings agent checks whether policies were followed and flags illogical/inconsistent reasoning). Evaluators run automatically on production traces using LangSmith's multi-turn evaluator with thread filters and sampling rates that start high and taper. Every production agent has a cloned **monitoring dashboard** (run volume, error rates, p50/p95 latency, token usage, tool-call success rates, LLM-judge scores over time), plus **PagerDuty alerts** (error rate > 5% or p95 latency > 10s over a 15-minute window pages the on-call engineer).

**The hard lesson:** the bottleneck was **prompt quality, not infrastructure**. Domain experts knew their issue types but struggled to translate that into reliably-followed LLM instructions; agents handled the happy path but fell apart on edge cases. Consistent failure modes: missing out-of-scope definitions, ambiguous branching logic, vague content guidelines. Lyft responded on two fronts: (1) a **structured prompt-writing framework** with five required components — **identity** (who/what user type/topic), **primary objective** (concrete verbs, not "help"/"handle"), **scope** (in-scope AND out-of-scope with explicit routing actions), **phased workflow** (numbered steps with entry conditions, branching for every if/else, a terminal action per phase), and **content guidelines** (concrete do/don't rules with example phrases) — paired with a review checklist ("does every phase have an exit?", "instructions for when a tool is unavailable?"); and (2) **automated prompt validation** — a Git-backed prompt **linting pipeline** that opens a PR against the config repo when a domain expert finishes a prompt, runs fast static rules (malformed template variables, duplicate intent slugs, spelling) then LLM-powered rules (prompt-injection vulnerabilities, contradictory instructions, structural dead-ends), and **blocks merge** on any violation, with inline UI feedback so the author can self-fix without an MLE. Key insight: **treat prompts like product specs, not code comments** — the more explicit the prompt, the more consistent the agent.

## Key Points

- **Self-serve platform thesis:** move agent development "closer to the people who understand customer issues best." Ops teams, VoC leads, and PMs define agents via prompts + configuration, reducing the need for MLEs to manage every iteration.
- **AI Assist scope:** rider + driver customer support across account access, damage claims, charge reviews, earnings disputes; millions of interactions. Journey began **2023**; each agent originally took **months** of MLE work.
- **Router multi-agent architecture on LangGraph.** A **meta agent** = stateful router; classifies request, dispatches via `Command(goto=...)` to a specialized **subagent**; each subagent is a full `StateGraph` registered as a subgraph node.
- **Separate router instances for riders vs drivers.** `rider_intent` (lost items, charge disputes, trip issues) and `driver_intent` (earnings, account access, damage claims). Mid-conversation, an intent agent can hand back via `Command(goto=..., graph=Command.PARENT)` for re-routing (e.g. driver-intent → damage-claim agent).
- **Safety runs in parallel at every turn**, before any LLM reasoning — malicious-intent detection and safety-issue detection execute concurrently via `Command(goto=[...])` fan-out.
- **Subagents are modular + independently deployable** — add an agent = define a new subgraph + register it.
- **Two agent categories:**
  - **Specialized agents** — hand-built by MLEs for complex/high-stakes flows (e.g. **damage claim agent**: image processing, fraud detection, multi-step classification, automation calls).
  - **Configurable agents** — self-serve; **initialized at runtime from JSON config** (internal config service) with **prompts from LangSmith Prompt Hub**; a `ConfigurableAgent` class does graph construction, tool binding, safety gates, state management. A PM can ship a new agent (e.g. driver tax questions) with a prompt + JSON config, **no MLE code changes**.
- **State persistence:** custom `DynamoDBSaver` implementing LangGraph's `BaseCheckpointSaver`; stores full graph state, execution metadata, parent-checkpoint references → conversation replay, debugging, state inspection.
- **LangSmith tracing:** every invocation across all envs (`LANGSMITH_TRACING=true`); captures nodes run, what the LLM saw, tools called, token usage, latency per step; enriched with metadata (user type, agent name, intent, conversation ID) for filtering; localize issues "within hours."
- **LLM-as-a-Judge evaluation pipeline (gate before 100% traffic):** small rollout (5–10%) → sample production traces as datasets → run LLM-judge evaluators (shared judge prompt from Prompt Hub + agent-specific metrics); LangSmith multi-turn evaluator with thread filters + tapering sampling rates. Domain-specific metric example: earnings agent checks policy adherence + flags illogical/inconsistent reasoning. **Tip from the post: use binary outputs (True/False, Pass/Fail), not scores, which are "inaccurate and non actionable."**
- **Production monitoring dashboards** per agent: run volume, error rates, p50/p95 latency, token usage, tool-call success rates, LLM-judge scores over time. **PagerDuty alerts:** error rate > 5% OR p95 latency > 10s over a 15-min window pages on-call.
- **The hard lesson — prompt quality is the bottleneck, not infrastructure.** Failure modes: missing out-of-scope definitions, ambiguous branching, vague content guidelines. "Treat prompts like product specs, not code comments."
- **Structured prompt-writing framework (five required components):** identity; primary objective (concrete verbs); scope (in-scope AND out-of-scope + routing actions); phased workflow (numbered steps, entry conditions, branching per if/else, terminal action per phase); content guidelines (concrete do/don't + example phrases) — plus a review checklist before activation.
- **Automated prompt validation (Git-backed linting, in development):** finishing a prompt opens a PR against the config repo; CI runs fast static rules (malformed variables, duplicate intent slugs, spelling) then LLM-powered rules (prompt-injection vulnerabilities, contradictory instructions, structural dead-ends); violations block merge; author gets inline UI feedback and self-fixes.
- **Results (since launch):** agent dev time **~6 months → ~2 weeks** for new configurable agents; a "growing number" of configurable agents in production plus several specialized agents; **100% of production agents** have automated LLM-as-a-Judge pipelines on live traces; **hallucination and contradiction rates down ~20%** (with hallucination guardrails built on LangSmith metrics); many non-engineers now build/iterate agents independently; **AI Resolution Rate up ~16%** since launching a few self-serve agents.
- **What's next:** complete the prompt-linting pipeline (zero manual MLE review for common errors); mocking/simulation infra for testing against synthetic conversations + mocked tools; pairwise evaluation (LangSmith Pairwise Annotation Queues for A/B'ing prompt revisions with human reviewers); expand to more geographies/user types (Freenow in Europe, AV support); deeper eval automation (continuous scoring on all traces + prompt-degradation alerts).
