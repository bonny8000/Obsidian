# Maintainability sensors for coding agents

**Authors:** Birgitta Böckeler (Distinguished Engineer and AI-assisted delivery expert, Thoughtworks)
**Published:** 2026-05-27 — martinfowler.com

## Summary

This is a practical, hands-on follow-up to Böckeler's earlier "harness engineering" mental model (a system of *guides* and *sensors* that raise the probability of good agent output and enable self-correction before issues reach humans). The article walks through her experiments using **sensors** to keep an AI-generated codebase maintainable. The test bed is an internal analytics dashboard for community managers — a TypeScript / Next.js / React app whose backend joins data from several APIs — which she deliberately rebuilt from scratch with AI and with almost no maintainability guides, to see how far sensor feedback alone could go. She defines maintainability as keeping change easy and low-risk over time ("internal quality"), and notes that internal-quality problems hurt AI agents the same way they hurt humans: an agent in a tangled codebase looks in the wrong place, creates duplicate-driven inconsistencies, or is forced to load more context than a task needs. The first visible cracks are when the number of files touched for a small change climbs, or when changes start breaking things that used to work.

She distinguishes **computational sensors** (deterministic — type checker, ESLint, Semgrep/SAST, dependency-cruiser, test coverage, mutation testing, GitLeaks) from **inferential sensors** (LLM-based reviews — security review, data-handling review, dependency-freshness report, modularity/coupling review). Sensors run at four points on the path to production: continuously **in-session** alongside the agent for fast feedback; again in the **CI pipeline** on clean infrastructure after integration; on a slower **scheduled** cadence to catch drift; and in **production** as runtime feedback. Her base harnesses were Cursor, Claude Code, and OpenCode (in that order), defaulting to Claude Sonnet, with Claude Opus for planning/analysis and Cursor's composer-2 for implementation.

On **basic linting (ESLint)**, the highest-value AI failure modes are max function arguments, file length, function length, and cyclomatic complexity — none active in ESLint's default preset, so she had to configure them. The key technique is a **custom ESLint formatter that overrides default messages with self-correction guidance** — a deliberate "good kind of prompt injection." The agent is told to make a judgment call and may suppress a warning *with a stated reason* (e.g. `// eslint-disable-next-line ... -- (reason)`), or *slightly raise a threshold* rather than face a binary suppress-or-comply choice; the rule then re-fires only if things get worse. This finally makes a clean linting baseline feasible, because suppressions stay visible and reviewable. Reviewing the agent's exceptions (suppressions, threshold bumps) became a great starting point for her code review. A telling observation: the agent kept raising the cyclomatic-complexity threshold — until she realized she had *no* self-correction guidance for that specific rule; adding guidance changed the behavior, proving the messages matter.

On **cross-file concerns**, she found a clear split. **dependency-cruiser** layered rules (e.g. `clients` must never import from `services`) worked well as live sensors to enforce folder structure and dependency direction, and the agent self-corrected against them — but they are limited to what is expressible via imports, file names, and folders. Raw **coupling metrics** (fan-in/fan-out, DSM) were largely **not useful to AI on its own**: when she gave an LLM only the coupling-analyser CLI output, its findings were "lackluster" — it flagged a deliberate DI-style factory and a shared zod schema (a legitimate frontend/backend contract) as problems. The deeper insight: *good* vs *bad* coupling is really about what is *appropriate*, which depends on context the raw graph lacks. By contrast, a fully **inferential AI modularity review** (using Vlad Khononov's "Modularity Skills") was "very fruitful," surfacing real, valid debt: duplicate route code across three near-identical endpoint files, inconsistent backend-calling (a third page reimplemented a hook two pages shared), request parameters repeated at every level (a date-range change had forced edits across 40+ files), and misplaced authentication/mock-fallback logic sitting inside the wiring factory. Grounding the inferential review in the coupling data added little; running it twice surfaced an extra issue, a reminder to run LLM analyses multiple times when it matters.

On **testing as a regression sensor**, she focused on test *effectiveness* (do tests catch breaking code), explicitly setting aside test *correctness* (are they testing the right behavior). The toolbox spans coverage, property-based testing, fuzz testing, and mutation testing; she used coverage and mutation testing. The headline finding: **coverage misleads** because a line being executed is not the same as its impact being verified. A `mappers.ts` file showed 100% statement / 75% branch coverage yet had no unit tests; **mutation testing with Stryker** reported 13 surviving mutants (the suite stayed green after 13 code mutations) — gaps an acceptance test had masked. Mutation testing is resource-intensive, so she ran incremental runs manually rather than continuously, and built a custom script to query Stryker's huge JSON report without clogging the agent's context ("AI helped me help AI"). Her conclusions: computational sensors shine at the file/function level but cross-file modularity needs an inferential (LLM) sensor for semantic interpretation; she worries about a **false sense of security** and **feedback overload** sending the agent into over-engineered refactoring spirals; she observed early signs of **conflicts between sensors** (max-lines/max-lines-per-function pushed complexity into long component property chains); and the **balance of guides vs sensors remains an open question** — which guides can be deleted once sensors are trusted, do sensors make weaker models viable, and how do you keep guides and sensors consistent. Without human review or AI modularity reviews, the agent was clearly compounding inadvertent technical debt.

## Key Points

- **Guides + sensors** are the two halves of a harness; sensors give the agent feedback so it can self-correct before issues reach humans. This article is the practical sensor follow-up to the harness-engineering model.
- **Computational vs inferential sensors.** Computational/deterministic: type checker, ESLint, Semgrep (SAST), dependency-cruiser, test coverage, mutation testing, GitLeaks. Inferential/LLM-based: security review, data-handling review, dependency-freshness report, modularity & coupling review.
- **Four places sensors run:** in-session (continuous, fast feedback), CI pipeline (re-run on clean infra after integration), scheduled (catch slow drift), and production (runtime feedback).
- **ESLint for AI failure modes:** max arguments, file length, function length, cyclomatic complexity — must be configured (not in the default preset). Third-party plugins targeting agent failure modes are emerging (e.g. Factory's eslint-plugin: require test files, structured logging).
- **Self-correction guidance via a custom ESLint formatter.** Override default messages with extra context. Allow the agent to suppress *with a stated reason*, or *slightly raise a threshold* (so the rule re-fires later) — avoiding a binary suppress-or-comply choice and keeping a clean, reviewable baseline.
- **Reviewing the agent's exceptions** (suppressions, threshold increases) is a strong code-review starting point. The agent kept bumping cyclomatic-complexity thresholds *because* that one rule lacked self-correction guidance — evidence that the custom messages genuinely shape behavior.
- **Context-sensitive rules** (e.g. `no-console`: use a logger in backend, avoid direct logging in frontend) are where AI's semantic judgment helps manage analysis warnings.
- **dependency-cruiser layered rules** (e.g. `clients` never imports `services`) work as live sensors: AI absorbed the steep config syntax cost, violated rules a few times, then self-corrected. Limited to what imports/file-names/folders can express. A rule requiring every new file to live in the predefined structure catches stray folders.
- **Raw coupling metrics are largely NOT useful to AI alone.** Given only CLI coupling data, the LLM flagged a deliberate DI factory and a legitimate shared zod schema ("god module") as issues. *Good* vs *bad* coupling is really *appropriate* vs not, and depends on context the import graph lacks. More practical use: human risk-triage during review (know the impact radius of changed files), or letting a review agent prioritize where it spends tokens.
- **Inferential AI modularity review (Vlad Khononov's "Modularity Skills") found real debt:** duplicate route code (3 near-identical endpoint files), inconsistent backend calls (third page reimplemented a shared hook), request params repeated at every level (a change touched 40+ files), and misplaced auth/mock-fallback logic inside the wiring factory. It also correctly recognized the "god module" hubs as purposeful. Grounding it in coupling data made little difference; a second run found an extra issue.
- **Test suite as regression sensor:** a failing pre-existing test forces the question "did I break it, or am I changing behavior intentionally?" — a good suite lowers the chance AI breaks wanted behavior. Article scopes to test *effectiveness*, not test *correctness*.
- **Coverage misleads; mutation testing (Stryker) catches missing assertions.** `mappers.ts`: 100% statement / 75% branch coverage but no unit tests and 13 surviving mutants — coverage shows a line ran, not that its impact was verified. Mutation testing is resource-intensive (run incrementally/manually). A custom query script keeps Stryker's huge JSON out of the agent's context.
- **Key takeaway:** computational sensors shine at the file/function level; cross-file modularity & coupling need inferential (LLM) sensors for semantic interpretation and trade-off judgment.
- **Risks & open questions:** false sense of security / illusion of quality; feedback overload → over-engineered refactoring spirals; conflicts between sensors (max-lines pushed complexity into long component prop chains); the balance of guides vs sensors (which guides to delete once sensors are trusted; do sensors enable weaker models; how to keep guides and sensors consistent and bundled). Sensors improve review trust but do not remove the human from the loop.
